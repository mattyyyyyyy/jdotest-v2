# 结构化访谈问题库 Interview Script

skill 在阶段 2 用本清单按 4 轮提问。每个问题包含：

- **问题**：实际向用户提的问题
- **理由**：为什么必须知道
- **决定**：影响哪些 ADR / 文档
- **默认假设**：用户答"待定 / 你推荐"时 skill 采用的保守值
- **后果**：默认值对项目的影响（用户应在多久内回来确认）

提问原则：

- 用 `AskUserQuestion` 工具批量问，每轮 3-4 题打包
- 问题尽量是选择题（含"其他"自定义），减少用户输入成本
- 推荐选项放第一位，加 "(推荐)" 后缀
- 用户答"待定" → 写 `docs/open-questions.md` + 用默认假设继续，不卡流程
- 一轮结束做"理解回放"：用 2-3 句复述关键决定让用户确认

## 轮 1 · 关键（必答）

### Q1.1 产品一句话定位

**问题**：用一句话描述产品 — 做什么、给谁用、解决什么问题？

**理由**：所有下游文档都引用这个定位。没有它，scope / constraints / architecture 都飘。

**决定**：`docs/project-brief.md` §问题 + §方案

**默认假设**：不允许默认。这是必答题，没有就不进入轮 2。

**后果**：硬卡点。

### Q1.2 当前阶段

**问题**：项目处于什么阶段？

- **纯想法**：还没有任何文档或代码
- **有 PRD / 需求文档**：可以贴路径或粘贴内容
- **有原型 / 设计稿**：Figma 链接或 mockup
- **已有仓库**：路径在哪，希望规范化什么
- **从其他项目迁移**：迁移源在哪

**理由**：决定 skill 从零生成还是先 audit 已有材料再补齐。

**决定**：阶段 1 的 intake 路径。已有仓库 → 先 `Read` 现有 `README.md` / `docs/` / `package.json` / `CLAUDE.md`。

**默认假设**：纯想法。

### Q1.3 MVP 范围与第一阶段切片

**问题**：第一阶段要演示的最小路径是什么？明确**不做**什么？

**理由**：避免范围爆炸。第一阶段切片越具体，task-plan 越能落地。

**决定**：`docs/scope.md` §MVP / §Out Of Scope / §第一条纵向切片

**默认假设**：把用户描述的最显眼场景作为切片，标 `[假设·待确认]`。

**后果**：切片选错会导致脚手架做无用功，应在 24 小时内回来确认。

### Q1.4 时间限制与目标交付

**问题**：什么时候要看到什么？

- **Demo**：本周 / 本月内有可演示版本，不上生产
- **MVP**：1-3 个月内对真实用户开放
- **生产**：3 个月以上，需要完整的可观测 / 合规 / 备份
- **持续演进**：无明确截止，按里程碑迭代

**理由**：决定要不要生成可观测 / 备份 / 灾备相关 ADR；决定测试覆盖深度。

**决定**：`docs/scope.md` §时间表 + 多个 ADR 的"后续事项"

**默认假设**：MVP，1-3 个月。

## 轮 2 · 架构（必答）

### Q2.1 技术栈倾向

**问题**：前端 / 后端 / 数据库技术栈有偏好吗？或者要 skill 推荐？

- **指定栈**：例如 React + Node + Postgres
- **方向倾向**：例如"JS 全栈"、"Python 后端"
- **完全待推荐**：基于项目类型和约束自动选

**理由**：每个栈选择都对应一个 ADR。

**决定**：ADR-0002（前端框架）/ ADR-0003（后端运行时）/ ADR-0004（数据库 ORM）

**默认假设**：基于项目类型推荐——产品型 web app 默认 React + Vite + TS / Node + Fastify + zod / PostgreSQL + Prisma；移动型默认 React Native + Expo；纯库默认对应语言 + 标准工具链。

### Q2.2 后端与数据存储

**问题**：项目需要哪些后端能力？

- **无后端**：纯前端 / 静态站
- **薄后端**：只有少量 API，无复杂业务逻辑
- **完整后端**：业务逻辑 + 数据库 + 鉴权
- **后端为主**：服务 / 数据管道 / 任务队列

**追问**（如果有后端）：是否需要数据库 / 缓存 / 消息队列 / 对象存储 / 任务队列？

**理由**：决定要不要生成 `backend-spec.md` / `api-contracts.md` / `integration-plan.md`。

**决定**：ADR-0003 / 0004 + `docs/backend-spec.md` 的有无

**默认假设**：薄后端 + Postgres + Redis（如有缓存需求）。

### Q2.3 鉴权与登录

**问题**：用户怎么登录？

- **无登录**：纯展示 / 内部工具
- **邮箱密码 + JWT**
- **手机号验证码**
- **OAuth / SSO**
- **平台 SDK**（微信 / Apple Sign-In / 车厂账号）
- **多种组合**

**理由**：鉴权是后端最容易做错的部分，必须前置定。

**决定**：ADR 单独一条（鉴权方案）+ `docs/api-contracts.md` §Auth

**默认假设**：邮箱密码 + JWT + bcrypt。

### Q2.4 部署目标

**问题**：跑在哪里？

- **云托管 PaaS**：Vercel / Railway / Fly.io / Render
- **云原生**：AWS / GCP / Azure + 容器
- **自建服务器**：物理机 / VPS
- **边缘 / CDN**：Cloudflare Workers / Vercel Edge
- **移动 / 桌面**：App Store / Play Store / 电子签名
- **嵌入式 / 车机 / IoT**：WebView / 内嵌 H5 / 固件

**理由**：决定 CI/CD、密钥管理、可观测性方案。

**决定**：ADR-0005（部署策略）+ `.env.example` 结构

**默认假设**：Vercel 前端 + Railway 后端。

### Q2.5 monorepo

**问题**：需不需要 monorepo？

- **单仓库 / 单项目**：一个 app，不拆 packages
- **monorepo**：多 app / 多服务 / 共享 packages
- **多 repo**：每个组件独立仓库

**理由**：影响目录结构和工具选型。

**决定**：ADR-0001（monorepo 工具）+ 目录结构

**默认假设**：项目类型决定——单应用默认单仓库，多端 / 服务 + 客户端默认 pnpm + Turborepo。

## 轮 3 · 约束（按需）

### Q3.1 合规要求

**问题**：有合规 / 法律 / 行业规范要求吗？

- **无**
- **GDPR / 隐私法**
- **PCI DSS**（支付）
- **HIPAA**（医疗）
- **等保 2.0 / 3.0**（中国）
- **行业特殊**（车规 / 金融 / 教育）

**理由**：合规决定数据留存、加密、审计日志、备份等等大量底层设计。

**决定**：`docs/constraints.md` §Business Rules + 多个 ADR 的"约束"

**默认假设**：无。

**后果**：如果实际有合规要求但默认成无，整个数据层可能要重做。强烈建议确认。

### Q3.2 性能红线

**问题**：性能目标？

- **首屏 FCP 目标**：≤ 1.5s / ≤ 2.5s / 不限
- **TTI 目标**
- **并发用户数**
- **响应延迟 P99**
- **Bundle 大小上限**

**理由**：决定要不要 SSR / CDN / 缓存策略。

**决定**：`docs/constraints.md` §Performance + ADR-0002 / 0005 的考量

**默认假设**：Web 产品默认 FCP ≤ 2.5s / TTI ≤ 4s / Bundle ≤ 500KB gzipped。

### Q3.3 设备 / 浏览器 / 分辨率

**问题**：目标设备和浏览器？

- **现代浏览器**：Chrome / Safari / Firefox 最新两版
- **包含旧浏览器**：IE / 老安卓 / 老 iOS
- **移动优先**：竖屏手机
- **桌面优先**：宽屏
- **特殊设备**：车机（横屏大屏）/ 平板 / IoT 屏 / 智能电视

**理由**：决定 polyfill 范围、CSS 写法、字号 / 触控目标。

**决定**：`docs/constraints.md` §Compatibility

**默认假设**：现代浏览器 + 桌面 / 移动响应式。

### Q3.4 安全红线

**问题**：有特别的安全要求？

- **数据归属**：用户数据存哪、可不可以出境
- **加密要求**：传输层、存储层、字段级
- **审计日志**：操作日志保留多久
- **API 限流 / 防爆破**
- **密钥管理**：KMS / Vault / 环境变量

**理由**：安全是后期最难补的部分。

**决定**：`docs/constraints.md` §Security + 后端 ADR 的考量

**默认假设**：传输 HTTPS + JWT + bcrypt + 关键操作有审计日志，密钥用 `.env` + 平台 secret manager。

### Q3.5 第三方集成 / 外部 API

**问题**：要集成哪些第三方？

- **支付**：Stripe / 支付宝 / 微信支付
- **通知**：邮件 / SMS / Push / WebSocket
- **存储**：S3 / 七牛 / OSS
- **AI 服务**：OpenAI / Anthropic / 本地模型
- **地图 / 定位**
- **分析 / 埋点**

**理由**：每个集成都要进 `docs/backend-spec.md` §Local Dependencies 并配 mock。

**默认假设**：无,按需后补。

### Q3.6 不能动的旧系统

**问题**：要兼容什么旧系统 / 已有 API？

- **数据库 schema 不变**
- **API 接口必须保持**
- **特定库版本**
- **特定运行时**

**理由**：旧系统约束是硬约束，必须前置写进 constraints。

**默认假设**：无。

## 轮 4 · 协作（按需）

### Q4.1 协作模式

**问题**：谁会动这个项目？

- **单 agent + 单用户**：只有你 + Claude
- **多 agent + 单用户**：Claude + Codex + GitHub Copilot 等并行
- **团队 + agent**：多人 + agent 协作
- **多人无 agent**：人类团队，agent 偶尔参与

**理由**：决定 `CLAUDE.md` 的厚度、`.claude/settings.json` hook 严格度、是否要 worklog。

**决定**：`CLAUDE.md` + `docs/INDEX.md` §Ownership Zones + `.claude/settings.json`

**默认假设**：单 agent + 单用户。

### Q4.2 路径所有权

**问题**：希望某些路径归特定角色 / agent 负责吗？

- **完全自由**：所有 agent 可以改任何文件
- **按目录分**：例如 docs/ 是产品 agent、apps/ 是工程 agent
- **按文件类型分**：例如 ADR 只能特定 agent 改

**理由**：决定 `Ownership Zones` 表的初始内容。

**默认假设**：单 agent 项目 → 全员；多 agent → 按 `apps/` / `services/` / `docs/` / `packages/` 粗分。

### Q4.3 review 与提交规范

**问题**：提交规范？

- **无规范**：直接 push 到 main
- **PR + self review**：开 PR 自己 merge
- **PR + 人类 review**：必须有人类 approve
- **PR + agent review**：用 `/code-review` / `/ultrareview` 检查后再 merge
- **conventional commits**：feat / fix / docs / chore

**默认假设**：PR + self review + conventional commits。

### Q4.4 hook 强制级别

**问题**：希望 hook 多严格？

- **宽松**：只配 commit 自报家门 / 密钥扫描
- **标准（推荐）**：开工三件套检查 + 测试 gate + 路径所有权
- **严格**：上述 + 文档同步强制 + ADR 前置 + append-only 越界拒绝

**理由**：决定 `.claude/settings.json` 的 hook 数量。

**默认假设**：标准。

## 理解回放模板

每轮结束后用类似这种格式简短回放：

```
轮 1 收到。我理解的关键决定：
- 你要做一个 [产品定位]
- 当前 [阶段]
- 第一阶段切片是 [演示路径]，明确不做 [排除项]
- 目标 [时间表]

确认 / 修正？
```

用户点头即进下一轮，有修正即就地更新。

---

## 不允许的提问反模式

- **一次问 5 个以上**：用户回答时会跳题
- **开放式 + 无默认**：用户卡住
- **问技术细节而不解释影响**：用户无法判断
- **重复问已知的事**：浪费来回；先读用户提供的 PRD / 仓库再问
- **问之后不回放**：用户不知道 skill 听懂没有
- **把"待定"当卡点**：所有项都有默认假设
