## Context

原生 Android 与后台共用 `services/api` 内存 store 和 `packages/order-state-machine`。当前 Compose 页面在发起网络请求后立即导航，导致目标页可能先于后端写入完成而加载；支付页甚至没有调用持久化端点。V3 Web 原型是视觉与交互基准，但原型自身的「我已支付」也只是页面跳转，因此原生落地需要补足真实业务闭环。

## Goals / Non-Goals

**Goals:**
- 让下单、立即购买、行车态再买、支付确认和订单查看形成真实前后台闭环。
- 让订单 UI 基于真实状态决定筛选、时间线和可用动作。
- 用自动化检查持续验证路由挂载和关键同步契约。

**Non-Goals:**
- 本轮不实现真实支付渠道、签名验签或生产支付回调鉴权。
- 本轮不把全部展示型页面改造成后端 CRUD 页面。
- 本轮不重画首页与商城首页。

## Decisions

1. 新增 `POST /api/v1/payments/:orderId/confirm` 作为 demo 支付回调模拟端点。端点内部只发送 `paid` 事件给共享状态机并持久化结果，消费端不能直接设置状态。
2. Android 共享状态层为异步操作增加主线程成功回调。页面只在后端操作成功后导航，避免请求与目标页加载之间的竞态。
3. 订单页保留真实后端订单作为首选数据源；仅在后端不可用或没有订单时显示演示样例。筛选和动作全部依据原始状态。
4. 回归分两层：API Vitest 覆盖状态持久化和后台可见性；Android 脚本覆盖路由装配、关键源代码契约、构建与可选模拟器 smoke。

## Risks / Trade-offs

- [Risk] demo 支付确认端点不具备生产支付回调安全性。→ 路径和文档明确标注为 confirm 模拟入口，后续接支付服务时替换。
- [Risk] 旧后端隧道离线时模拟器端到端测试会失败。→ 脚本将静态契约、API 本地测试和模拟器测试分层输出。
- [Risk] 展示型页面仍存在与 V3 Web 的细节差异。→ 审计文档区分闭环缺陷与视觉细节，后续按页面继续收敛。
